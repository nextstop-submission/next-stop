# 배송지 직접 추가 — 설계와 실측

출발 전, 정차(P) 상태에서 배송지를 한 곳씩 더하는 기능이다. 지금까지는 내비의 최근 목적지·즐겨찾기를 가져오는 길만 있었다.

## 조건

- NaviHelper 3.0.5에는 주소·장소를 좌표로 바꾸는 검색 API가 없다. `requestRoute(RouteInfo)`는 위도·경도를 받는다 🔧 SDK.
- 외부 지도 API·서버·키를 쓰지 않는다. APK에 비밀 키를 넣지 않는다.
- Android 기본 지오코더(`android.location.Geocoder`)는 공식 에뮬레이터 이미지에 없다: `Geocoder.isPresent()=false` ✅ 실측(CI 2회차, `probe-results/ci-20261031-0249/navi-lab`). 키 없이 주소를 좌표로 바꿀 길이 차 안에는 없다.

## 두 방식 비교

| | A. 차 안에서 정차 중 입력 | B. 폰에서 주소 목록을 넘김 |
|---|---|---|
| 주소 → 좌표 | Pleos 내비의 장소 검색이 한다(키 불필요) | 폰이나 서버에서 지오코딩해야 한다 → 지도 API 키나 서버가 필요 |
| 키·서버 | 없음 | 폰 앱에 키를 넣거나 서버를 둬야 한다(경계 위반) |
| 차와 연결 | 없음(차 안에서 끝) | 폰↔차 전송 길이 따로 필요(공개 SDK에 없음) |
| 주행 제한 | 정차(P)에서만 입력칸을 연다. 주행 중엔 화면에 없음 | 운전 중 조작 없음 |
| 입력 품질 | 내비가 고른 POI라 좌표·건물 이름이 정확하다 | 주소 문자열이 틀리면 좌표가 틀린다 |
| 결론 | **채택** | 키·서버 없이는 불가 → 채택 안 함 |

B의 쓸모 있는 부분은 이미 있다. 폰 지도 앱에서 '차로 보내기'로 보낸 목적지는 내비 최근 목적지에 쌓이고, 다음집은 '최근 목적지 가져오기'로 그것을 배송지로 읽는다(실측 확인 — 최근 목적지·즐겨찾기 각 2건 수신).

## 흐름 (A)

1. 계획 화면 '배송지 추가'에 장소 이름을 쓰고 **내비에서 찾기** → `requestNavigationScreen(SearchPlace(검색어))`로 Pleos 내비의 장소 검색 화면을 연다(`NAVI_CUSTOM_MAP`).
   - 검색 화면 요청이 듣지 않는 내비라면 **내비 열어 고르기** → `requestNavigationScreen(Foreground)`. 사용자가 내비에서 직접 검색해 목적지로 정한다.
2. 사용자가 결과 하나를 목적지로 정하면 내비가 `onDestinationChanged`를 보낸다 → 앱이 `getDestinationInfo()`로 좌표·이름·주소·POI ID를 받는다. 앱이 뒤에 있다가 돌아와도(`onResume`) 한 번 더 묻는다.
3. 받은 곳을 배송지에 더한다(`core/model/StopEdit.add`): 같은 POI이거나 30m 안이면 새 줄을 만들지 않고 그 집의 소포 수를 1 늘린다. 최대 30곳.
4. 고른 곳으로 안내가 시작되지 않게 경로를 취소한다(순서는 앱이 정한다). 앱이 뒤에 있었으면 '배송지 추가됨' 알림을 띄운다.
5. 목록은 파일에 저장된다(`plan-stops.txt`) — 앱이 뒤에서 종료돼도 남는다.

틀리게 받지 않게 막은 것(`core/model/PlaceCapture.kt`, 테스트 5개):

- 검색을 연 뒤 10분 안의 목적지만 받는다. 한 번 받으면 대기를 끝낸다.
- 목적지 없음(내비가 좌표 0,0을 돌려줌 ✅ 실측)은 무시한다.
- 검색을 열기 직전에 내비에 있던 목적지는 '원래 있던 것'으로 적어 두고 받지 않는다 — 돌아와서 옛 목적지를 새로 고른 곳으로 착각하지 않게.
- 방금 받은 곳이 다시 읽히면(취소 전 캐시) 소포 수를 또 늘리지 않는다.

편집: 줄마다 **삭제**, **순서 고정**을 켜면 ▲로 순서를 옮긴다(꺼 두면 앱이 최적 순서를 계산), **모두 지우기**. 운행 중에는 편집하지 않는다.

CI(GitHub Actions)의 내비는 그래픽 없이 돌아 지도를 그리지 못한다. 그래서 '사람이 검색 결과를 고르는' 마지막 고리는 노트북 에뮬레이터에서 잰다.
