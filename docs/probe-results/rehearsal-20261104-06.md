### 5-10. 정리

- 목표였던 '5회 연속 C 5/5·B 5/5'는 **달성하지 못했다.** 가장 길게 이어진 것은 3회 연속이다(5차 42d5b6d·b4ebaf8·3b1919d, 9차 090c576·41b80bf·ed98d68).
  - 2차 묶음은 환경이 정상이던 4회가 모두 5/5였다. 나머지 1회는 기기 정지였다.
- C를 실제로 돈 39회 가운데 C 5/5는 14회다(3차 묶음 5회는 스크립트 오류라 무효). B는 기기가 멈춘 회차를 빼면 1회(4/5) 말고 모두 5/5다.
- **앱 결함 4건을 찾아 고쳤다.**
  - 포그라운드 서비스 10초 기한을 넘겨 강제 종료되던 것
  - Car 서비스에 다시 붙지 않던 것
  - 재생성 때 `reset`이 다시 적용되던 것
  - 직접 읽기를 메인 스레드에서 하던 것(ANR 위험)
  - 마지막 수정(재생성 `reset`)은 GitHub Actions 결제 한도로 에뮬레이터 리허설을 다시 돌리지 못했다. 로컬 단위·화면 테스트로만 확인했다.
- **앱 밖 원인(환경)은 고칠 수 없었다.**
  - Virtual Console의 기어 변경이 차량 값(VHAL)에 늦게(최대 약 2분) 반영되거나 끝내 반영되지 않았다. 2초 직접 읽기로도 값이 바뀌지 않아, 앱이 받기 전 단계의 문제로 판단했다.
  - VC 문 토글이 굳었다(스크립트로 우회했다).
  - 에뮬레이터 프레임워크가 정지했다(화면 검정·`dumpsys` 무응답).
  - 내비가 앞에 있을 때 시스템이 앱 프로세스를 종료했다(포그라운드 서비스 중에도).
- 신호 지연(VC 요청 → 앱 수신)
  - 정상 회차의 중앙값은 0.2~16초다. 날마다, 러너마다 크게 다르다.
  - 짝이 어긋나지 않은 회차의 최대는 21초다.
  - '최대 100초 이상'으로 찍힌 값은 앞 신호가 유실돼 다음 신호와 짝지어진 것이다(`c-latency.tsv`의 짝짓기는 시간순 첫 일치).
  - 기획서의 '신호→판정 1초 안팎'은 이 실측과 맞지 않는다. '수 초~십여 초(에뮬레이터 VC 경로)'로 고쳐야 한다(문서는 다른 사람 몫).
- 60초 문 보정 창을 120초 이상으로 늘리면 VC 기어 유실 회차 몇 개는 '건수'가 맞았을 것이다. 하지만 실차 근거 없이 리허설 통과용으로 늘리지 않았다.
  - 보정 손잡이(adb `--el door_before_park_ms`)로 바꿀 수 있다.
